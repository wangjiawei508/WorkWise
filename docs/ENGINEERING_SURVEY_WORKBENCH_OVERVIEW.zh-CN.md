## 1. 文档目的

本文档用于完整说明 WorkWise Survey 工作台当前的产品定位、业务范围、系统架构、已实现能力、验证证据、尚未完成事项和后续建设重点。WorkWise 是通用桌面 AI Agent 平台，Survey 是第五个工作台；RAILWISE Survey 仅指商业发行版。开源平台与商业能力归属仍为 Q-40 待决事项。

本文中的状态按以下口径区分：

- **已实现**：仓库中已有可执行代码和对应接口。
- **已验证**：已有自动化测试、构建或端到端运行证据。
- **待验收**：代码基本具备，但尚未在最终打包应用和真实使用环境中完成验收。
- **规划中**：OpenSpec 或设计文档中已经定义，但尚未完成实现与验证。

本文不把设计目标视为已交付能力，也不把源码测试或 Mock 结果替代最终安装包验收。本文不得作为“已通过 GB 55018-2021 测评或试验验证”的宣称或证据；Q-39 尚未关闭，只能称具备内部测试或候选验证材料。

## 2. 总体结论

截至 2026-09-04，Survey 工作台已经从单一表单或计算页面发展为一套覆盖工程项目、数据治理、质量校核、测量平差、变形分析、AI 编排、候选成果生成和草稿审阅的内部候选系统。

当前可以形成如下判断：

> 工程项目管理、监测数据处理、主要测量平差策略、变形分析、AI 任务编排及内部候选成果/技术追溯链路已打通；F-AUD-14、F-QC、F-OUT-11、软件测评或试验验证和正式交付均未完成。剩余关键工作主要集中在 P0 专业测量格式证据、最终候选包 GUI 验收、签名公证和跨平台验证。

从内部试用角度看，系统已经具备较完整基础；从工程生产环境和正式公开发布角度看，当前仍属于 0.5.0 开发分支或私有候选阶段，不能视为已正式发布。

## 3. 产品定位

工程测量工作台不是把通用聊天界面简单换成工程术语，也不是只提供几个测量计算器。它的目标是把专业工程测量任务组织为一条可恢复、可审批、可验证、可追溯的交付链路。

核心定位包括：

1. **工程项目是业务边界**：数据、分析、测量网络、成果和审查记录均归属于明确项目。
2. **AI Agent 是协调者**：负责理解目标、形成计划、解释结果、调用工具和组织交付。
3. **确定性 Runtime 是数值真源**：观测值、闭合差、残差、协方差、精度和变形量均由确定性算法生成。
4. **人工草稿审阅是当前门禁**：风险步骤、警告接受和候选成果固化需要明确状态与审查动作；这不替代法定过程检查、最终检查或验收。
5. **候选成果必须可技术追溯**：每份候选报告和证据包都关联输入、算法、版本、引用和运行记录；这不等同于 F-AUD-14 或正式交付。
6. **历史数据必须兼容**：迁移采用增量、延迟和非破坏方式，不静默删除已有线程、文件、插件、Skill、MCP、凭据或用户数据。

## 5. 用户工作流

### 5.1 AI 优先工作流

AI 优先工作流面向希望用自然语言完成复杂任务的用户：

1. 用户进入工程测量工作台并选择或创建项目。
2. 用户描述任务目标并附加数据或资料。
3. Agent 读取受限工程上下文，生成类型化计划。
4. 系统校验计划中的工具、输入、修订状态和风险步骤。
5. 用户对需要授权的步骤进行审批。
6. 已批准计划进入统一 `TaskController → AgentLoop` 执行链路。
7. RailWise 工具调用确定性工程服务和测量内核。
8. 指标、异常、引用、成果文件和运行状态以证据卡形式回流。
9. 用户复核结果并进入候选成果预览、草稿审阅和候选固化。

AI 不直接成为测量数字的来源。模型只接收项目摘要、数据摘要、哈希、修订号和证据索引，避免把大规模原始观测数据送入模型上下文。

### 5.2 经典确定性工作流

经典工作流为专业用户提供明确的分阶段操作入口：

1. 项目配置；
2. 数据资产；
3. 质量校核；
4. 趋势分析或测量平差；
5. 报告与证据包；
6. 草稿审阅和候选成果固化。

经典入口也是 AI 不可用、模型不可用或需要人工逐项处理时的兼容表面。

## 6. 前端工作台现状

### 6.1 工作台入口与隔离

工程测量工作台已经注册为独立懒加载工作台。工程侧栏只展示当前工作区的工程测量项目，不再混入普通编程线程。

工程会话通过 `domain: "engineering"` 和 `projectId` 与其他工作台隔离。Code、Write、Design 和 Engineering 在切换路由后分别保持自己的会话时间线和选中状态。

项目选择、项目创建和返回工程页面使用持久化项目 ID 与应用事件衔接。近期修复已经覆盖重启后恢复工程项目线程、审批计划和测量运行。

### 6.2 AI Agent 工作表面

`EngineeringAiCommandCenter` 已改造为三栏式工程 Agent 界面：

- 左侧：任务执行阶段、当前计划与运行进度；
- 中央：真实 ChatState 会话、附件、目标输入、审批和运行消息；
- 右侧：Copilot 证据检查器，展示质量发现、指标、趋势、引用和成果；
- 顶部状态带：当前项目、Agent 当前动作、运行门禁和下一步动作。

当前页面已经接入真实的计划创建、计划查询、审批、启动和证据读取接口，不再使用组件局部的 `localStorage` 线程指针或独立 SSE 模拟链路。

### 6.3 交付控制台

工作台经典首屏已经从导入表单改成“交付控制台”，展示六个阶段及其完成状态：

### 6.4 专业测量工作区

`SurveyAdjustmentPanel` 已经从 JSON 主界面调整为专业测量工作区，当前包含：

## 7. Runtime 与数据层现状

### 7.1 工程服务

`EngineeringService` 当前承担：

- 工程项目创建、修改与读取；
- 数据集导入、标准化和持久化；
- 数据质量检查与人工接受警告；
- 确定性监测分析；
- 图表和报告预览；
- 候选成果固化与 manifest 生成；
- 工程运行记录、取消和恢复；
- 修订冲突和幂等控制。

数据通过 SQLite Repository 持久化。原始附件由统一 Attachment Store 管理，候选成果写入项目工作区内的受控目录。成果修订不可覆盖不等同于 F-AUD-14；原始观测不可修改、派生修正、返工任务、签名与二级检查仍须按 PRD 独立实现与验收。

### 7.2 AI 编排服务

`EngineeringContextService` 负责生成有边界的工程上下文快照，包含项目、数据集、引用、来源、修订和哈希信息。

`EngineeringAiOrchestrator` 负责：

- 类型化计划解析；
- 工具和步骤校验；
- 审批令牌；
- 幂等控制；
- 修订冲突和过期计划处理；
- TaskRun 提交；
- 运行事件投影；
- 取消和恢复。

AI 批准后的执行统一进入已有任务引擎，没有建立第二套工程队列，也不允许 AI 编排层绕过 TaskRun 直接把工程运行标记为完成。

内核提供：

- 有界稠密/稀疏矩阵计算；
- 加权最小二乘；
- 约束和最小约束求解；
- 秩和条件数诊断；
- 协方差传播；
- 残差和标准化残差；
- 精度统计；
- 迭代收敛诊断；
- 取消检查点；
- 确定性输入和运行哈希；
- 点数、观测数、未知参数和矩阵非零元素上限。

### 9.3 数值安全边界

当前设计明确禁止以下降级行为：

- 未知网络类型不得自动套用通用平面网算法；
- GNSS 缺少向量、协方差、基准或端点坐标时必须阻断；
- 坐标转换缺少参数或有效控制点时不得使用零参数或恒等转换；
- 三角网几何不成立时不得返回成功；
- 超过计算规模上限时不得先分配巨型矩阵再报错；
- AI 不得改写确定性结果中的数值和单位。

## 10. 变形分析能力

系统能够基于不可变的不同期次平差结果进行比较，当前覆盖：

- 三维坐标差 `dX`、`dY`、`dH`；
- 沉降量；
- 水平位移；
- 倾斜；
- 收敛；
- 变化速率；
- 时间趋势；
- 结果质量与来源关联。

期次比较基于明确的参考平差和当前平差 ID，不直接覆盖历史结果，从而保留重新计算和审计能力。

## 11. 内部候选成果与技术追溯

本章仅说明内部候选成果与技术追溯，不代表过程检查、最终检查、合同验收、批准交付或 F-OUT-11 合规交付。

当前候选成果链路支持：

- 趋势图；
- `report.docx`；
- `report.pdf`；
- `evidence.xlsx`；
- `manifest.json`。

成果包关联：

- 项目 ID 和项目修订；
- 数据集 ID 和数据修订；
- 分析 ID；
- 平差结果 ID；
- 变形比较 ID；
- 输入哈希；
- 算法与工具版本；
- 单位和精度元数据；
- 规范、知识库或附件引用；
- 警告与人工接受状态；
- 输出文件路径和摘要。

候选成果预览与候选固化是两个不同阶段。固化后不原地覆盖；后续数据、字段映射、阈值或算法变化需要产生新的候选成果修订。该机制不等同于 F-AUD-14 的完整工序门禁、返工、签名和二级检查。

当前的“不可覆盖”与来源/输出哈希复核是本地 Runtime 的应用层边界：它防止常规 API 路径把跨项目、失效来源或被替换的输出带入新的计算和候选交付，并通过重新读取、哈希比对和确定性重算暴露不一致。它不是对可直接修改 SQLite、数据库 schema 或项目工作区的主体提供的密码学防篡改证明；若 F-AUD 后续需要对抗该威胁模型，仍须补充外部签名或见证锚点、密钥管理，以及跨 Runtime 实例的事务性发布机制。

## 16. 主要风险

### 16.1 格式接入风险

厂商格式差异大，部分格式封闭或需要外部转换器。若缺少内容签名、版本识别、原始记录定位和来源保留，错误解析可能进入平差链路并造成严重结果偏差。

应坚持：无法可靠识别时保留原文件并阻断，不把未知二进制文件降级为通用表格解析。

### 16.2 专业正确性风险

测量场景不能用单一通用最小二乘模板覆盖所有网型。每种策略需要独立的观测方程、约束、权模型、几何条件和负面样本。

当前已经按策略拆分，但仍需持续用权威算例和真实项目进行对照验证。

### 16.3 产品体验风险

如果入口仍表现为后台表单、JSON 编辑器或大量无层次卡片，即使内核正确，也难以获得专业用户信任。近期 UI 重构已经改善结构，但最终判断必须来自打包应用和专业人员实测。

### 16.4 验收与发布风险

源码构建通过不能替代：

- 精确候选包启动；
- 最终 UI 截图；
- 真机操作；
- 正式签名公证；
- Windows 验证；
- updater 往返；
- 用户对精确版本的发布确认。

## 19. 最终结论

工程测量工作台当前已经拥有清晰的产品骨架和较扎实的确定性计算底座。其核心价值不只是“会算平差”，而是把工程目标、原始资料、质量门禁、专业计算、AI 协作、成果文件和人工审查组织成同一条可追溯链路。

目前最值得肯定的是：

- AI 与确定性数值责任边界已经明确；
- 工程运行进入统一任务引擎，没有形成双轨状态系统；
- 主要测量策略不再依赖通用算法兜底；
- 成果已经具备修订、证据和 manifest；
- 工作台正在从 Web 后台式页面向专业测量软件和 Agent 工作区融合演进。

目前最需要集中投入的是：

- 多厂商专业测量源格式；
- 导入前的格式识别、诊断和准备状态；
- 最新候选包中的完整专业体验验收；
- 签名、公证、Windows 和 updater 发布闭环。

在这些事项完成之前，工程测量工作台适合继续作为内部开发与候选验证能力推进，不应对外宣称为已经完成发布的 0.5.0 正式版。
