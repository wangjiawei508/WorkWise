# 声明式质检整改与复查链

本增量补齐 P1 质量流程中“声明检查 → 登记问题 → 记录整改 → 声明复查”的持久化与桌面入口。它记录用户声明及所引用的真实保全文件，不判断缺陷是否属实，不认证检查人员，不产生专业签章或交付批准。既有材料保全检查仍只表示文件字节完整，原成果的草稿状态不变。

## 操作流程

1. 在成果审查的“材料保全与检查记录”中，冻结当前成果资料并创建或恢复检查记录。
2. 展开“声明检查与整改链”，创建独立记录或恢复其历史。该记录固定绑定当前项目修订、保全计划、检查记录及链头。
3. 登记“检查未通过”或“尚未评估”，填写可辨识的检查编号，并选择实际保全的依据文件。
4. 从非通过检查中登记问题，填写问题编号并确认这是一条声明记录。
5. 生成修改后的独立成果清单，在其材料保全入口冻结新成果并创建检查记录。回到原整改链，选择同项目的这份保全成果，填写整改编号与依据文件。相同成果不能冒充整改成果。
6. 选择尚未解决的问题和其当前整改成果，登记“声明已解决”或“声明仍未解决”。查看审计明细可追踪每条声明的编号、材料与链头。声明已解决不等于专业验收通过。

修改原成果文件或继续追加已绑定保全记录，都会使旧绑定失效；系统会显示来源变化，不自动改绑到最新记录。应先完成资料保全再创建整改链。网络失败时使用同一操作的重试，以保留幂等键；切换项目、成果、修订或断开 Runtime 会使过期展示和后续写入失效。

## 实现与兼容边界

- 独立 `survey-quality-workflow.sqlite3` 保留工作流、声明事件及本地链头，禁止更新、删除与替换。旧 `survey-quality.sqlite3` 及其检查读取逻辑不变。
- 项目级认证 API 使用 `/v1/engineering/projects/:projectId/quality-workflows`，支持创建、分页历史、读取和追加事件。严格请求合同不接受人员身份、规范通过、签名或批准字段；摘要由 Runtime 从真实保全记录解析生成。
- 每次读写校验项目修订/工作目录、SQL 与 JSON 身份、请求摘要、序列、链头和实际来源。独立的两轮来源读取检测校验过程中的变化，并在每轮去重重复来源。容量限制由[合同](../../kun/src/contracts/survey-quality-workflow.ts)给定。
- 所有输出保留 `caller-declared-workflow-only`、`checkpointTrust: local-records-only`、`standardConformity/humanSignatureVerification: not-evaluated` 和 `deliveryApproval: not-granted`。本地链头不能证明独立保管或抵抗整库替换。
- 这不完成完整组织阶段、缺陷分类、整改后重新抽样、真实签章、受信规则执行、生产总体认证或整个 P1。新增界面还需要自己的签名候选包和用户确认，旧候选不包含本次增量。
