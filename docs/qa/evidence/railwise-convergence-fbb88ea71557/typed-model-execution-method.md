## What Was Prepared and What Actually Ran

The plane-control source, project, review cards and typed plan were synthetic acceptance fixtures. The plan was not generated by a model in this run. After GUI approval/start, the official `deepseek-flash` endpoint supplied the model responses through a temporary authenticated loopback relay. The model requested four actual packaged Runtime tools in this order:

1. `survey_network_validate`
2. `control_network`
3. `survey_adjustment_read`
4. `report_export`

The relay allowed those four tools plus the packaged typed-plan policy's read-only `survey_read_context`. This fifth tool was advertised but was not called. The original relay report retains its older `four typed measurement tools` label; the audit records the correction without altering the original report.

The relay report records five chat-completion requests and three model-list requests, all HTTP 200, with no failed request. Its code forwards original provider bytes after checking tools and scope. It generates no assistant answer or deterministic tool result. Follow-up tool messages must equal the same-call-ID output persisted in the isolated candidate thread. The only URL exception is the exact static `parameters.$schema` JSON Schema identifier; other URL payloads remain rejected.

## Independent Checks

The audit opens only the candidate's engineering, Survey, plan and task SQLite databases using `readOnly: true`. It reads only the named project, network, plan, task and thread records. Append-only thread item revisions are deduplicated by item ID before counting four calls and four successful results.

All four plan steps are approved. Recorded step parameters equal the approved parameters with predecessor bindings resolved and the deterministic idempotency key added. Step handles match the corresponding tool outputs. Persisted thread arguments are deliberately redacted to `{}` by the application, so parameter verification uses the separate plan-step evidence rows and does not infer missing arguments from assistant prose.

The adjustment output and subsequent read output are equal. Every returned deterministic result field matches the stored Survey adjustment. The report contains that same full adjustment result and only the specified synthetic source. The task's final answer matches the persisted final assistant message; it is not used as the source of numerical verification.

The three files are read from the candidate workspace and checked against both recorded byte counts and SHA-256 values. DOCX and XLSX pass ZIP CRC32 validation and contain the required OOXML content type and main XML entry. XLSX contains 15 worksheets. `pdfinfo` parses the PDF as 2 pages. These are structural and integrity checks, not visual report-layout acceptance.

Database and WAL hashes remain unchanged across this audit. The temporary session token file is absent, the stopped loopback port refuses connections, all eight credential fields in candidate settings are empty, the Runtime configuration contains no credential-value fields, and the provider base URL is restored to the official endpoint. Credential values are never emitted or archived.

## Reproduction

Requirements: a Node version with `node:sqlite`, the retained exact candidate and local evidence, and `pdfinfo` on `PATH`. The verifier uses JSZip bundled with the candidate. It writes no candidate data and makes no model request; its only connection attempt checks that the stopped loopback port is closed.

```sh
node verify-typed-model-execution.mjs '<candidate-root>' '<this-evidence-directory>' '<stopped-relay-port>'
node --test railwise-typed-acceptance-relay.test.mjs
```

The relay's 13 self-tests use synthetic keys and mocked upstream responses. They separately test five-tool scope, genuine candidate storage layout, readonly source loading, exact result binding, foreign project/source rejection, URL exceptions, authentication, stream validation, cancellation and token cleanup. They are helper tests, not the evidence for the real model execution.
