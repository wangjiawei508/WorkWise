## 已核实的流程要求

| 条款 | 印刷页 / PDF 页 | 核查结论及实现含义 |
| --- | --- | --- |
| 4.1 | 3 / 6 | 检查依据包括项目标准、批准的设计及补充文件、委托/合同/任务文件和验收委托文件。不能仅选一个国标编号就产生完整检查计划。 |
| 4.2.1 | 3 / 6 | 短引文：“各阶段应独立、按顺序进行”。阶段为过程检查、最终检查、验收检验，不能省略、替代或倒序。三个代理标签不能证明组织独立。 |
| 4.2.2 | 3 / 6 | 过程检查由测绘单位作业部门承担，实施全数检查；完成并确认修改无误后才转最终检查。 |
| 4.2.3 | 3 / 6 | 最终检查由测绘单位质量管理部门组织；内业全数检查，野外检查项可按第 5 章抽样；应评定单位成果及批质量等级、编写检查报告，确认修改无误后转验收。 |
| 4.2.4 | 3 / 6 | 验收由委托单位组织，或委托有资质的质量检验机构承担；核验最终检查，可按第 5 章抽样；评定单位成果、样本和批质量，编制检验报告，修改确认后提交。 |
| 4.5.1-4.5.2 | 4 / 7 | 短引文：“经检查者、复核者签字后一般不得更改”。应保留各阶段全部检查记录；报告完整并随成果归档。事件哈希完整不等于检查者和复核者已经签字。 |
| 4.6.1-4.6.3 | 4 / 7 | 问题要改正；最终检查不合格的单位成果处理后重检；验收不合格批退回处理，经检查合格后再申请，重新抽样。不能只删除失败事件或复用前次样本。 |

软件的“最终成果 SHA-256”是绑定具体文件的工程措施，并非标准直接规定了 SHA-256。现有 `evaluateSurveyFinalArtifactCoverage` 对同一最终摘要、独立检查点、必检项和改正后重检的要求可保留，但只是事件覆盖判断，不能替代上述组织职责、阶段先后和签字。

## 抽样与质量评定

| 条款 | 印刷页 / PDF 页 | 已核实的规则与边界 |
| --- | --- | --- |
| 3.2-3.7、5.1 | 1、5 / 4、8 | 先确定成果类别、单位成果、批和质量元素。批量不是观测条数、文件数或未知点数。单位成果可为点、测段、网等，必须按相应成果类别确定。 |
| 5.2、表 1 | 5 / 8 | 按批量区间查样本量；样本量大于或等于批量时全数检查。例：批量 1-20 对应样本量 3；21-40 对应 5；687-1000 对应 56。总数达到 1001 时应分多个检验批，批次数最小、各批数量均匀。完整表仍须作为独立核对后的版本化数据输入。 |
| 5.3.1-5.3.3 | 5-6 / 8-9 | 样本分布均匀，宜简单随机，也可按作业单位、工序/时段、地形或方法分层按比例随机抽取；抽中单位成果应含全部资料及规定补充材料。抽样记录须保留总体、分层、方法、抽中结果和证据，不能只给抽样数量。 |
| 6.1.1-6.1.3 | 6 / 9 | 样本详查，按需对样本外成果概查。概查通常记录 A、B 类错漏及普遍性问题；单位成果无 A 类且 B 类少于 4 个才概查合格。这不是全体单位成果详查的通用通过规则。 |
| 6.2.1.2 | 6 / 9 | 检出 A 类错漏，或任一质量元素、子元素得分低于 60，单位成果不合格。先执行这些否决条件，不能靠其他元素高分抵消。 |
| 6.2.2-6.2.3 | 6 / 9 | 质量元素、子元素、权及错漏分类按第 7 章；一般不调整权。仅检查部分元素时按规定相对权重调整，并保持总和 1.0，不能为绕过失败项任意删除必检项。 |
| 6.2.4.1-6.2.4.3、表 2 | 6-7 / 9-10 | 数学精度存在检测评分和错漏扣分两种路径；B/C/D 扣分为 `12/t`、`4/t`、`1/t`，通常 `t=1`，调整须经委托方批准。表 2 同时列 A 类 42 分，但 A 类已触发 6.2.1.2 不合格，不能只扣分后继续评为合格。 |
| 6.2.4.4-6.2.5、表 3 | 7-8 / 10-11 | 子元素到元素、元素到单位成果按权聚合；全部元素及子元素至少 60 分才进行单位成果等级评定：优为至少 90，良为至少 75 且低于 90，合格为至少 60 且低于 75。 |
| 6.3 | 8 / 11 | 样本含任一不合格单位成果即样本不合格；全部合格后才能以算术平均分评定样本等级。不能用平均分遮蔽不合格单位成果。 |
| 6.4.1-6.4.2 | 8 / 11 | 最终检查批等级与验收批判定不同：前者在批成果合格后按优良品率/优级品率评等级；后者依详查、已实施的概查判批合格与否。未实施概查时按详查；发现伪造成果或技术路线重大偏差则批不合格。 |

第 4.3.4 条（印刷页 4 / PDF 页 7）原文对检测点数使用“少于 20”和“大于 20”，本次扫描页未明确恰为 20 的分支。若实现数学精度检测评分，需记录该边界并取得解释依据，不能默默写成 `n >= 20`。本研究不将该条编入自动规则。

## 当前内业成果的分类约束

第 7.5.1 条与表 43-44（印刷页 57-60 / PDF 页 60-63）适用于工程测量的平面控制测量，表 43 标注单位为“点”。第 7.5.2 条与表 45-46（印刷页 61-63 / PDF 页 64-66）适用于工程测量的高程控制测量，表 45 标注单位为“测段”。这两类均需检查数据质量、点位质量和资料质量，不能只检查平差精度。

因此当前 GSI 导入产生的 28 条原始边、14 条参考路线、21 个未知点不能直接充当同一“批量”；应依据真实项目定义测段、单位成果及批边界，再冻结检查总体。算法运行成功也不能证明仪器检定、埋石、托管、设计审批及资料归档满足要求。缺证项目保持未评估。

表 44、46 的横线表示相应质量（子）元素不存在该类错漏，不是通用的零扣分项；未注明错漏数量按表下注处理。完整错漏分类仍需逐项版本化和独立复核。本记录没有复制整张分类表或声称全部映射完成。附录 A（资料性）印刷页 114-115 / PDF 页 117-118 提供检查记录表参考，含处理意见、修改、复核、错漏类别以及检查者/复核者与日期；不能把资料性表式本身当成人员身份认证机制。

## 最小持久化与接口方案

以下为实施建议，不是已实现功能。沿用 `EngineeringService` 的 SQLite 和现有单一 Runtime HTTP 边界，不增加第二套后台。

1. 新建不可变的 `survey_quality_plans`：固定项目、成果类别、单位成果总体与字节摘要、批/分层、标准精确版本、批准设计等依据、完整必检项、各阶段职责及批准证据。检查计划独立保存，不能从通过结果反推。修订生成新计划版本。
2. 新建 `survey_quality_records` / `survey_quality_events`：用记录 ID 隔离同一项目的不同成果链；事件保留现有 V1 哈希语义，按记录 ID 和序号设置唯一约束。追加事务同时检查 `expectedHeadHash`、幂等键和项目/计划/成果绑定，服务端确定序号、时间和记录主体。不能接受调用者填写的任意 `human` 身份或把字符串角色升级为认证身份。
3. 另存抽样记录和结构化错漏证据：保留单位成果 ID、总体摘要、样本方法、可复现随机来源/算法版本、抽中名单、检查范围、A/B/C/D 分类依据、处理意见和整改/复核关联。重抽必须生成新记录并保留旧记录，不覆盖历史。先支持记录和复验，再实现经核对的分类与评分计算。
4. 用内容寻址存储保留实际证据文件，并核验摘要、字节数、读取权限及项目归属。既有草稿 manifest 和输出文件组成冻结检查目标；质检结果先放关联 sidecar/数据库记录，避免把待签质检摘要写回被检查 manifest 造成自引用。交付复验重新读取目标实际字节。
5. 首批接口可为 `GET /v1/engineering/projects/:projectId/quality-records`、`POST /v1/engineering/projects/:projectId/quality-records`、`POST /v1/engineering/quality-records/:recordId/events` 和 `POST /v1/engineering/quality-records/:recordId/verify-final`。验证请求只引用服务端已冻结的计划和目标，不能从请求直接接受必检列表、通过结果或独立检查点；跨项目、旧 head、证据不存在返回明确错误。
6. 检查点须由独立受信保管方留存，或由与写入事件不同的信任边界签署并留存回执。同一 SQLite 内的另一张表只能改善一致性，不能证明对数据库整体改写/回滚的抵抗能力。没有外部保管证据时仍显示记录覆盖状态，不授予验收状态。
7. 接入现有 `verifyDeliverable` 时新增质量记录覆盖、依据版本、真实文件和签认状态；保留旧草稿 manifest 读取，不回填旧记录为通过。覆盖完整仍维持 `reviewStatus: draft`，直至真实检查、复核和批准证据齐备。

持久化首批验证至少覆盖重启读取、并发追加、幂等重放冲突、链尾截断、总体或检查计划换版、抽样名单替换、跨项目证据、同成果重检、修改后的旧签认失效以及旧 manifest 兼容。现有单元函数测试不能替代这些端到端证据。

## 规则来源与人员身份边界

现有 `SurveyStandardRegistry` 仅支持有限标量谓词，并要求全文摘要、条款字节区间摘要和独立审核的完整规则摘要。扫描 PDF 的页码与人工转述不满足该条款字节语义要求；不能拿一个随意 PDF 字节区间冒充可核对的条文文本。下一步应增加与原 PDF 哈希、页号、页面区域和图像摘要绑定的来源类型，保留转录文本及复核摘要；旧 V1 保持可读。流程、抽样和层级评分则应采用有版本的专用合同/纯函数，不能硬塞进单个 `lte`。

机器可核实文件完整性、确定性计算及已记录的状态，不能自行证明现场事实和组织独立。真实签认至少应绑定检查/复核人员、所属组织与角色、项目授权及有效时间、明确签认意图、计划版本、最终成果与记录摘要。采用数字签名时，还需验证证书/密钥归属、授权链、签名覆盖和适用的有效性状态；仅有姓名、账号、图片签名或 `actor.kind = human` 均不足。标准本身没有在上述条款中指定必须采用某种数字签名技术，该建议属于软件证据设计。

多个 AI 智能体可以交叉审查条款转录、样本边界和实现，但仍必须记录 `agent` 身份，不能模拟成作业部门、质管部门、委托单位或有资质检验机构。组织资格、个人授权、项目适用性及真实签字未验证时，`standardConformity` 与 `humanSignatureVerification` 应继续为 `not-evaluated`。
